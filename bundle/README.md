# STACKIT Connectors Bundle

A ready-to-run [Camunda 8 Connector Runtime](https://docs.camunda.io/docs/components/connectors/custom-built-connectors/connector-sdk/)
that already contains every STACKIT connector in this repository. It is an ordinary Spring Boot
application: one jar, one container, one process.

```
de.envite.camunda.stackit:stackit-connectors-bundle
  -> stackit-connectors-bundle-<version>-with-dependencies.jar
  -> bundle/Dockerfile -> envite/stackit-connectors:<tag>
```

## Contents

| Connector | Job type | Element template |
| --- | --- | --- |
| STACKIT Object Storage | `de.envite:stackit-object-storage:1` | `de.envite.connectors.stackit.objectstorage.v1` |

The runtime discovers connectors through their
`META-INF/services/io.camunda.connector.api.outbound.OutboundConnectorFunction` entries, so this
table is generated by nothing - it is kept in step by `StackitConnectorsApplicationTest`, which
asserts against the runtime's own connector registry.

## When to use this, and when not to

There are three ways to get a custom connector into a Camunda 8 installation. Camunda does not host
third-party connector code, so one of them is always required.

| | What you deploy | Use it when |
| --- | --- | --- |
| **1. Mount into Camunda's bundle** | `stackit-connector-<service>-<version>-with-dependencies.jar` mounted into `camunda/connectors-bundle` | You already run `camunda/connectors-bundle` and want STACKIT connectors **next to** Camunda's own HTTP/Kafka/AWS connectors. One runtime, one set of credentials, one thing to monitor. |
| **2. Run this bundle** | `envite/stackit-connectors` (this module) | You want only STACKIT connectors, or you want them isolated from Camunda's connectors - separate scaling, separate restart blast radius, separate log stream. Also the simplest option when you have no connector runtime yet. |
| **3. Camunda 8 Run** | `stackit-connector-<service>-<version>-with-dependencies.jar` dropped into `custom_connectors/` | Local development against the single-process Camunda 8 Run distribution. |

**Prefer option 1 if you already run `camunda/connectors-bundle.`** Running both that image and this
one against the same cluster is supported, but two runtimes that activate the same job type will
race for every job, so never deploy the STACKIT connectors twice.

### Option 1 - mount the shaded jar into `camunda/connectors-bundle`

The mount path differs by target, and getting it wrong produces a runtime that starts cleanly and
simply never registers the connector.

Self-Managed (the connector lands on the runtime's own classpath):

```bash
docker run --rm --name stackit-connector \
  -v "$PWD/stackit-connector-object-storage-<version>-with-dependencies.jar:/opt/app/connector.jar" \
  --network camunda \
  -e CAMUNDA_CLIENT_MODE=self-managed \
  -e CAMUNDA_CLIENT_GRPCADDRESS=http://orchestration:26500 \
  -e CAMUNDA_CLIENT_RESTADDRESS=http://orchestration:8080 \
  -e SECRET_STACKIT_S3_ACCESS_KEY='<access key>' \
  -e SECRET_STACKIT_S3_SECRET_ACCESS_KEY='<secret access key>' \
  camunda/connectors-bundle:<version>
```

Attached to Camunda SaaS (hybrid mode) the path is `/opt/custom/connector.jar` **and**
`LOADER_PATH` has to point at that directory - see [Hybrid mode](#hybrid-mode-attaching-to-camunda-saas)
below for the full command.

Source: [Host custom connectors](https://docs.camunda.io/docs/components/connectors/custom-built-connectors/host-custom-connectors/).
Note that at the time of writing that page's Self-Managed examples still use the pre-8.8
`CAMUNDA_CLIENT_BROKER_GATEWAY-ADDRESS`, `CAMUNDA_OPERATE_CLIENT_*` and `CAMUNDA_IDENTITY_*`
variables. The mount paths are current; the variable names in the snippets above are the 8.8+
Camunda Spring Boot Starter ones from
[Use connectors in hybrid mode](https://docs.camunda.io/docs/guides/use-connectors-in-hybrid-mode/)
and the [properties reference](https://docs.camunda.io/docs/apis-tools/camunda-spring-boot-starter/properties-reference/).

### Option 3 - Camunda 8 Run

Drop `stackit-connector-<service>-<version>-with-dependencies.jar` into the `custom_connectors/`
directory of the Camunda 8 Run setup root and restart it. Secrets for Camunda 8 Run go into
`connector-secrets.txt` in the same root, one `NAME=VALUE` per line.

> Not verified against a running Camunda 8 Run installation. `custom_connectors/` and
> `connector-secrets.txt` are not described on the *Host custom connectors* page; check the
> [Camunda 8 Run](https://docs.camunda.io/docs/self-managed/quickstart/developer-quickstart/c8run/)
> documentation for your exact version before relying on the file names.

## Running it

### From the jar

```bash
./mvnw -B -DskipTests -pl bundle -am package
java -jar bundle/target/stackit-connectors-bundle-*-with-dependencies.jar
```

Requires Java 21. The defaults in
[`src/main/resources/application.yaml`](src/main/resources/application.yaml) point at a
Self-Managed Orchestration Cluster on `localhost`, so with the Camunda Docker Compose distribution
running this needs no further configuration.

### With Docker

The Dockerfile lives in `bundle/` but the **build context is the repository root**, because the
bundle is the last module of a multi-module reactor and needs its siblings' sources:

```bash
docker build -f bundle/Dockerfile -t envite/stackit-connectors:dev .
```

(from the repository root; the trailing `.` is the context). The build uses BuildKit cache mounts
for the Maven repository, so it needs Docker 23+ or `DOCKER_BUILDKIT=1`.

```bash
docker run --rm -p 8086:8080 \
  -e CAMUNDA_CLIENT_MODE=self-managed \
  -e CAMUNDA_CLIENT_GRPCADDRESS=http://host.docker.internal:26500 \
  -e CAMUNDA_CLIENT_RESTADDRESS=http://host.docker.internal:8080 \
  -e SECRET_STACKIT_S3_ACCESS_KEY='<access key>' \
  -e SECRET_STACKIT_S3_SECRET_ACCESS_KEY='<secret access key>' \
  envite/stackit-connectors:dev
```

The image runs as UID/GID 1001, exposes 8080, and carries a `HEALTHCHECK` against
`/actuator/health/readiness`. Anything appended after the image name is passed to Spring Boot as an
application argument, so `... envite/stackit-connectors:dev --server.port=9090` works.

[`examples/docker-compose.yml`](../examples/docker-compose.yml) wires this together with an
Orchestration Cluster for a complete local setup.

## Configuration reference

Every setting is a Spring Boot property, so each has an environment-variable form: uppercase it,
**drop the dashes**, and replace the dots with underscores - `camunda.client.grpc-address` becomes
`CAMUNDA_CLIENT_GRPCADDRESS`. Values set in the environment win over `application.yaml`.

### Cluster connection

| Environment variable | Property | Meaning | Default |
| --- | --- | --- | --- |
| `CAMUNDA_CLIENT_MODE` | `camunda.client.mode` | `self-managed` or `saas`. Each mode supplies its own defaults for the addresses below. | `self-managed` (set by this bundle) |
| `CAMUNDA_CLIENT_GRPCADDRESS` | `camunda.client.grpc-address` | Gateway gRPC endpoint; jobs are activated over this. Scheme required. | `http://localhost:26500` (set by this bundle) |
| `CAMUNDA_CLIENT_RESTADDRESS` | `camunda.client.rest-address` | Orchestration Cluster REST endpoint, used for topology and the document store. | `http://localhost:8080` (set by this bundle) |
| `CAMUNDA_CLIENT_AUTH_METHOD` | `camunda.client.auth.method` | `none`, `basic` or `oidc`. | `none` |
| `CAMUNDA_CLIENT_AUTH_USERNAME` / `..._PASSWORD` | `camunda.client.auth.username` / `.password` | Basic authentication. Setting either implies `basic`. | unset |
| `CAMUNDA_CLIENT_AUTH_CLIENTID` / `..._CLIENTSECRET` | `camunda.client.auth.client-id` / `.client-secret` | OIDC client credentials. | unset |
| `CAMUNDA_CLIENT_AUTH_TOKENURL` | `camunda.client.auth.token-url` | OIDC token endpoint. Set automatically in `saas` mode. | unset |
| `CAMUNDA_CLIENT_AUTH_AUDIENCE` | `camunda.client.auth.audience` | OIDC audience. Set automatically in `saas` mode. | unset |
| `CAMUNDA_CLIENT_CLOUD_CLUSTERID` | `camunda.client.cloud.cluster-id` | SaaS cluster id. Required in `saas` mode. | unset |
| `CAMUNDA_CLIENT_CLOUD_REGION` | `camunda.client.cloud.region` | SaaS cluster region. Required in `saas` mode. | unset |
| `CAMUNDA_CLIENT_TENANTID` | `camunda.client.tenant-id` | Default tenant for cluster operations. | `<default>` |
| `CAMUNDA_CLIENT_WORKER_DEFAULTS_TENANTIDS` | `camunda.client.worker.defaults.tenant-ids` | Tenants whose jobs are activated. | `<default>` |
| `JAVAX_NET_SSL_TRUSTSTORE` / `..._TRUSTSTOREPASSWORD` | - | Custom trust store, for a cluster behind a private CA. | JDK default |

### Job workers

| Environment variable | Property | Meaning | Default |
| --- | --- | --- | --- |
| `CAMUNDA_CLIENT_WORKER_DEFAULTS_MAXJOBSACTIVE` | `camunda.client.worker.defaults.max-jobs-active` | In-flight jobs per connector worker. | `100` (set by this bundle; the starter's own default is `32`) |
| `CAMUNDA_CLIENT_WORKER_DEFAULTS_STREAMENABLED` | `camunda.client.worker.defaults.stream-enabled` | Job streaming instead of pure polling. | `true` (set by this bundle; the starter's own default is `false`) |
| `CAMUNDA_CLIENT_WORKER_DEFAULTS_TIMEOUT` | `camunda.client.worker.defaults.timeout` | How long an activated job stays locked. | `PT5M` |
| `CAMUNDA_CLIENT_WORKER_DEFAULTS_ENABLED` | `camunda.client.worker.defaults.enabled` | Set to `false` to start the runtime without opening any worker. | `true` |
| `CONNECTOR_<NAME>_TIMEOUT` | - | Per-connector job timeout in milliseconds. `<NAME>` is the connector's declared name, uppercased with `_` for separators. | per connector |
| `CONNECTOR_OUTBOUND_DISABLED` | - | Comma-separated connector **types** to leave unregistered. | unset |
| `CONNECTOR_OUTBOUND_DISCOVERY_DISABLED` | - | Disables `META-INF/services` discovery entirely. Setting this empties this bundle. | unset |

### Secrets

| Environment variable | Property | Meaning | Default |
| --- | --- | --- | --- |
| `CAMUNDA_CONNECTOR_SECRETPROVIDER_ENVIRONMENT_ENABLED` | `camunda.connector.secretprovider.environment.enabled` | Resolve `{{secrets.NAME}}` from environment variables. | `true` |
| `CAMUNDA_CONNECTOR_SECRETPROVIDER_ENVIRONMENT_PREFIX` | `camunda.connector.secretprovider.environment.prefix` | Prefix prepended before the lookup. | `SECRET_` |
| `CAMUNDA_CONNECTOR_SECRETPROVIDER_ENVIRONMENT_TENANTAWARE` | `camunda.connector.secretprovider.environment.tenantaware` | Changes the variable name to `${prefix}${tenantId}_${name}`. | `false` |
| `CAMUNDA_CONNECTOR_SECRETPROVIDER_CONSOLE_ENABLED` | `camunda.connector.secretprovider.console.enabled` | Fetch secrets from Camunda Hub / Console. Only for SaaS-managed secrets in hybrid mode. | `false` |
| `CAMUNDA_CONNECTOR_SECRETRESOLVER_SECRETFILTER_MODE` | `camunda.connector.secret-resolver.secret-filter.mode` | `STRICT`, `LAX` or `DISABLED`. Under `STRICT` a secret only resolves in the field that declares it. | `STRICT` |

> **Mind the spelling if you configure these in YAML rather than the environment.** The runtime
> reads the secret-provider settings through `@Value("${camunda.connector.secretprovider...}")` -
> *without* a dash in `secretprovider` - while the secret-*resolver* settings really are
> `secret-resolver.secret-filter`. Camunda's documentation sometimes writes the first group as
> `camunda.connector.secret-provider.…`; that form binds into a metadata-only record and has no
> effect. The environment-variable forms in the first column work for both, because Spring's
> relaxed binding strips the dashes anyway - which is why this table and
> `examples/docker-compose.yml` use environment variables throughout.

### Observability

| Environment variable | Property | Meaning | Default |
| --- | --- | --- | --- |
| `SERVER_PORT` | `server.port` | HTTP port for the actuator endpoints. | `8080` (set by this bundle) |
| `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE` | `management.endpoints.web.exposure.include` | Which actuator endpoints are served. | `health,metrics,loggers` (set by this bundle) |
| `LOGGING_LEVEL_IO_CAMUNDA_CONNECTOR` | `logging.level.io.camunda.connector` | Runtime log level. `DEBUG` shows job activation and secret resolution. | `INFO` (set by this bundle) |
| `LOGGING_LEVEL_DE_ENVITE_CAMUNDA_STACKIT` | `logging.level.de.envite.camunda.stackit` | STACKIT connector log level. | `INFO` (set by this bundle) |
| `CAMUNDA_CONNECTOR_POLLING_ENABLED` | `camunda.connector.polling.enabled` | Process-definition polling, needed only by **inbound** connectors. | `false` (set by this bundle - see below) |

Endpoints: `/actuator/health`, `/actuator/health/readiness` (cluster reachable),
`/actuator/health/liveness`, `/actuator/health/startup`, `/actuator/metrics`, `/actuator/loggers`.
**None of them is authenticated** - do not publish this port outside the deployment.

There is no `/actuator/prometheus`: the bundle's classpath carries `micrometer-core` but no
registry implementation, so the endpoint does not exist. Add
`io.micrometer:micrometer-registry-prometheus` to `bundle/pom.xml` and append `prometheus` to
`MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE` to get it.

### Why inbound polling is off

Every STACKIT connector is outbound. The process-definition poll loop exists so the runtime can
find **inbound** connector elements in deployed models, so with no inbound connector on the
classpath it only generates cluster traffic. If you add an inbound connector to this runtime, set
`CAMUNDA_CONNECTOR_POLLING_ENABLED=true`, or its triggers will never activate.

### Adding more connectors

Add the module as a dependency of `bundle/pom.xml` and rebuild - the `META-INF/services` entry in
that module does the rest, and `StackitConnectorsApplicationTest` will see it. This image
deliberately does **not** support a `/opt/custom` drop-in directory: the jar is repackaged with the
default Spring Boot layout, whose launcher ignores `loader.path`. To drop a jar into a runtime
without rebuilding, use `camunda/connectors-bundle` with `LOADER_PATH` (option 1 above).

## Supplying secrets

A connector field written as `{{secrets.STACKIT_S3_ACCESS_KEY}}` is resolved by the **connector
runtime**. Since Camunda 8.9 the environment secret provider prepends `SECRET_`, so that reference
reads the environment variable `SECRET_STACKIT_S3_ACCESS_KEY`:

```bash
docker run --rm \
  -e SECRET_STACKIT_S3_ACCESS_KEY='<access key>' \
  -e SECRET_STACKIT_S3_SECRET_ACCESS_KEY='<secret access key>' \
  envite/stackit-connectors:dev
```

`--env-file` works too, and in Kubernetes the usual shape is a `Secret` consumed with `envFrom`,
whose keys are already named `SECRET_...`.

Two sharp edges:

* **A secret that does not resolve is not an error at startup.** It surfaces as an incident on the
  first job. If the connector reports an authentication failure, check the variable name first.
* `CAMUNDA_CONNECTOR_SECRETPROVIDER_ENVIRONMENT_PREFIX=` (empty) turns *every* environment variable
  into a readable secret. The runtime logs a warning when you do this. Don't.

### The newer `camunda.secrets.<name>` syntax

Camunda 8.9 added `camunda.secrets.<name>`, used in a FEEL input mapping
(`=camunda.secrets.STACKIT_S3_ACCESS_KEY`). It is resolved by the **Orchestration Cluster** before
the job is activated, not by this runtime, and it is the recommended form for new models - the
secret never reaches the connector runtime's environment at all. It needs a secret store
configured on the cluster, so this bundle's own configuration has nothing to do with it. Names must
match `[\p{Alnum}_-]+`, and a name containing `-` needs FEEL backticks:
``=camunda.secrets.`my-key` ``.

The legacy `{{secrets.NAME}}` form remains fully supported, and is what
`examples/bpmn/stackit-object-storage-example.bpmn` uses, because it works with nothing but an
environment variable on this container.

Sources: [Connectors configuration](https://docs.camunda.io/docs/self-managed/components/connectors/connectors-configuration/),
[Migrate secrets](https://docs.camunda.io/docs/components/connectors/use-connectors/migrate-secrets/).

## Hybrid mode: attaching to Camunda SaaS

A customer-managed connector runtime attached to a SaaS cluster is the **only** way a custom
connector reaches Camunda SaaS - Camunda-managed SaaS runtimes execute only Camunda's own
connectors.

Prerequisites, from
[Use connectors in hybrid mode](https://docs.camunda.io/docs/guides/use-connectors-in-hybrid-mode/):

* A client ID / client secret pair with the **Orchestration Cluster REST API** scope.
* The **Secrets** scope as well, if you want the runtime to read SaaS-managed secrets.
* The cluster id and region, from the cluster's detail page in Console.

```bash
docker run --rm --name stackit-connectors-hybrid \
  -e CAMUNDA_CLIENT_MODE=saas \
  -e CAMUNDA_CLIENT_CLOUD_CLUSTERID='<cluster id>' \
  -e CAMUNDA_CLIENT_CLOUD_REGION='<region>' \
  -e CAMUNDA_CLIENT_AUTH_CLIENTID='<client id>' \
  -e CAMUNDA_CLIENT_AUTH_CLIENTSECRET='<client secret>' \
  -e SECRET_STACKIT_S3_ACCESS_KEY='<access key>' \
  -e SECRET_STACKIT_S3_SECRET_ACCESS_KEY='<secret access key>' \
  envite/stackit-connectors:dev
```

In `saas` mode the gRPC and REST addresses are templated from the cluster id and region, so leave
`CAMUNDA_CLIENT_GRPCADDRESS` and `CAMUNDA_CLIENT_RESTADDRESS` unset.

To use secrets you manage in Camunda Console instead of environment variables, add
`CAMUNDA_CONNECTOR_SECRETPROVIDER_CONSOLE_ENABLED=true` and give the API client the `Secrets`
scope.

Three things that will cost you an afternoon if you get them wrong:

* **Never use `camunda/connectors-bundle-saas`.** It is Camunda-internal, intended for
  Camunda-managed runtimes, and will not work for a customer-managed one. If you are using option 1
  rather than this bundle, the image is `camunda/connectors-bundle`.
* **Leave `CAMUNDA_CONNECTOR_RUNTIME_SAAS` unset.** Connectors test for the variable's *presence*,
  not its value, so setting it to `false` still switches on SaaS-only validation. Symptoms are
  startup or validation errors mentioning `defaultCredentialsChainUsedInSaaS`, `must be false`, or
  `camunda.connector.auth.issuer`. `CAMUNDA_CLIENT_MODE=saas` is a different setting and is correct
  to keep.
* **Operate is not required.** Since Camunda 8.8 the connector runtime talks to the Orchestration
  Cluster through the Camunda Spring Boot Starter properties above. Any guide still setting
  `CAMUNDA_OPERATE_CLIENT_URL`, `CAMUNDA_IDENTITY_*` or `ZEEBE_AUTHORIZATION_SERVER_URL` predates
  that and does not apply here.

### Element templates in hybrid mode

Unlike Camunda's own connectors, the STACKIT connectors need no `CONNECTOR_<NAME>_TYPE` override
and no edited "hybrid" template. That mechanism exists to stop a *Camunda-managed* SaaS runtime
from stealing jobs of a type it also knows - it rewrites `io.camunda:http-json:1` to
`io.camunda:http-json:local`. `de.envite:stackit-object-storage:1` is not a type any Camunda
runtime knows, so no SaaS runtime will ever activate it. Install the template from
`connectors/object-storage/element-templates/` unchanged.

A `hybrid/` variant of the template is generated anyway, for consistency with Camunda's own
connectors and for the case where someone does want to pin a local type.

## Monitoring

```bash
curl -s localhost:8086/actuator/health | jq
curl -s localhost:8086/actuator/health/readiness
curl -s localhost:8086/actuator/metrics | jq '.names | map(select(startswith("camunda")))'
```

`readiness` reports `DOWN` until a topology request to the cluster succeeds; that is the signal to
alert on, and it is what the image's `HEALTHCHECK` uses. The startup probe flips to `UP` once the
Spring context is ready, and `liveness` tracks cluster reachability. While
`camunda.connector.polling.enabled` is `false`, the `processDefinitionImport` component reports
`UP` with `operateEnabled: false` - that is expected, not a misconfiguration.

## Development

```bash
./mvnw -pl bundle -am -B verify            # build and run the smoke test
./mvnw -pl bundle -am -B -DskipTests package
docker build -f bundle/Dockerfile -t envite/stackit-connectors:dev .
```

`StackitConnectorsApplicationTest` starts the full Spring context and asserts that the Object
Storage connector is present in the runtime's registry and instantiable. It needs no Camunda
cluster: the client connects lazily and the test closes the job workers with
`camunda.client.worker.defaults.enabled=false`.
